# Аудит готовности Atlas к настольной Windows-сборке

Дата аудита: 9 августа 2026 года. Исходная точка: `75d00bc`.

## Краткий вывод

Atlas можно превратить в удобное полностью локальное приложение без Docker и
Ollama. Переписывать интерфейс и RAG для этого не требуется. Наиболее надежная
первая архитектура:

```text
ярлык Atlas
  -> локальный супервизор
      -> llama-server + GGUF (CPU обязательно, GPU по возможности)
      -> упакованный Python 3.11 + текущий Streamlit backend
      -> http://127.0.0.1:<локальный порт> в браузере

%LOCALAPPDATA%\Atlas\
  data\        SQLite, FAISS, документы, задания и вложения
  models\      GGUF, embeddings, reranker, OCR и Whisper
  logs\        диагностические журналы без содержимого документов
  versions\    устанавливаемые версии приложения
```

Docker в этой схеме не маскируется: он отсутствует. Ollama также не нужен:
`llama-server` является небольшим движком инференса, которым управляет сам
Atlas. Streamlit остается внутренним локальным web-интерфейсом. WebView можно
добавить позже, но для первого пилота системный браузер проще диагностировать и
не меняет пользовательские функции.

Docker-редакция при этом сохраняется как отдельный рабочий продукт для
разработки и личного использования автора. Desktop не меняет `compose.yaml`,
Ollama-модель, проектные `data/` и `model_cache/`; её бинарники, GGUF и staging
не публикуются внутри Docker-образа.

Удобство «из коробки» достижимо, однако модель 4–6B Q4 нельзя считать
равноценной текущей 9B во всех задачах. На сложном коде, длинных ответах и
грязном OCR снижение качества может быть заметно. До фиксации модели нужен
приемочный набор реальных обезличенных задач Atlas. Архитектура должна разрешать
отдельную установку более крупного GGUF без переустановки приложения.

## Что сейчас от чего зависит

| Компонент | Текущая роль | Что делать в desktop-сборке |
|---|---|---|
| Docker | Python/Linux-окружение, системные пакеты, запуск Streamlit | Исключить; заменить упакованным Windows backend |
| Ollama | Список моделей, контекст и генерация по HTTP | Заменить управляемым `llama-server`; оставить Ollama как режим разработки |
| Python 3.11 | Вся логика UI, RAG, парсинга, OCR и обезличивания | Поставлять внутри приложения; системный Python не нужен |
| Streamlit | Существующий интерфейс | Сохранить, слушать только `127.0.0.1`, запускать автоматически |
| PyTorch + torchvision | Sentence Transformers и EasyOCR | Включить CPU-сборку; это один из самых тяжелых компонентов |
| Sentence Transformers | `multilingual-e5-base` и cross-encoder reranker | На первом этапе сохранить ради качества и совместимости индекса |
| FAISS CPU | Постоянный dense-индекс | Включить Windows DLL/wheel и проверить чтение существующего индекса |
| SQLite FTS5 | База, история и дисковый lexical index | Использовать SQLite из поставляемого Python; отдельно проверить FTS5 |
| EasyOCR + OpenCV | Изображения, сканы и производственные отчеты | Поставлять модели `ru/en`, CPU обязателен; текущий код явно задает `gpu=False` |
| faster-whisper | Расшифровка аудио моделью `small`, CPU int8 | Включить CTranslate2 и модель заранее либо отдельным подписанным model pack |
| FFmpeg | Медиа-декодирование и диагностика аудио | Поставлять Windows-бинарники с notices |
| LibreOffice | Только конвертация бинарного `.doc` в DOCX/HTML | Включить headless-компонент или отдельный обязательный legacy pack; без него функция `.doc` теряется |
| pandas/openpyxl/python-docx/lxml/PyMuPDF/Pillow | Таблицы, Office и PDF | Поставлять в Python backend |
| cryptography/Argon2 | Ключи обратимого обезличивания | Поставлять бинарные зависимости; ключи не включать в обновления или логи |
| Caddy | Только удаленный Docker-профиль | Не включать в локальную desktop-сборку |
| Linux `libgl/libglib/libgomp` и fonts | Зависимости контейнерных wheels/OCR | На Windows заменить DLL wheels, VC++ runtime и проверенным набором шрифтов |
| Браузер/WebView2 | Отображение локального UI | Для v1 открыть браузер; WebView2 рассматривать после пилота |

На проверенной рабочей копии `model_cache` занимает 1,61 GiB и уже содержит
embedding-модель, reranker и EasyOCR. Модель Whisper в этот объем может не
входить, если аудио еще не обрабатывалось. `data` занимает 0,059 GiB и должно
всегда обновляться отдельно от приложения.

Собранный в ходе аудита Linux-образ без ML-кэша имеет content size 1,06 GB;
внутри него `/usr/local` с Python и wheels занимает 2,4 GB, а LibreOffice —
219 MB. Windows-размер не будет идентичен, но этот замер подтверждает порядок
оценки backend-компонентов и показывает, что основную массу дают ML wheels, а не
Streamlit или код Atlas.

## Реалистичные варианты

| Вариант | Плюсы | Риски | Решение |
|---|---|---|---|
| Docker/WSL внутри установщика | Почти нет изменений кода | Виртуализация, права, большой слой, сложный запуск и обновление | Отклонить |
| Скрыто установить Ollama | Минимум изменений LLM-клиента | Второй продукт, служба и собственный updater; это именно маскировка Ollama | Не использовать для desktop v1 |
| `llama-server` + упакованный Python + браузер | Сохраняет Atlas, простой HTTP-шов, явное управление процессами и моделями | Нужно проверить Windows wheels, lifecycle и установщик | Рекомендуется |
| То же + WebView2 shell | Вид обычного desktop-приложения | Еще один runtime, окна/скачивания/диагностика | После стабильного браузерного пилота |
| Переписать backend на .NET/Rust/ONNX | Потенциально меньший runtime | Большой объем работ и риск изменить OCR/RAG/Office-поведение | Не для первой версии |

## Предварительный ресурсный бюджет

Числа являются диапазонами до сборки воспроизводимого прототипа.

| Ресурс | Реалистичная оценка |
|---|---|
| GGUF 4–6B Q4 | примерно 2,5–3,8 GiB на диске |
| Текущий ML-кэш RAG/OCR | 1,61 GiB по факту этой рабочей копии |
| Whisper small | ориентировочно еще 0,4–0,8 GiB |
| Python, wheels и native DLL | ориентировочно 1–2,5 GiB после установки |
| LibreOffice + FFmpeg + llama.cpp | ориентировочно 0,7–1,3 GiB |
| Полная установка | ориентировочно 6–9 GiB без пользовательских данных |
| RAM для обычного чата/RAG | ориентировочно 6–9 GiB рабочего набора |
| Пиковая RAM при OCR/индексации | ориентировочно 8–12 GiB; нужен замер |
| Минимальная машина | Windows 10/11 x64, 16 GiB RAM, CPU-режим |
| Комфортная машина | 24–32 GiB RAM; GPU с 6+ GiB VRAM полезен, но не обязателен |

Целевая конфигурация с 8 GiB RAM и GPU до 8 GiB рассматривается как отдельный
ограниченный профиль. Qwen3.5-4B Q4_K_M помещается в такую VRAM, но полная
CPU-only работа одновременно с PyTorch, embeddings/reranker и OCR в 8 GiB RAM
пока не доказана. Для неё потребуется ленивый запуск и явная выгрузка тяжёлых
подсистем; до измерения нельзя заявлять 8 GiB RAM гарантированным минимумом.

На современном desktop CPU 4–6B Q4 обычно пригодна для интерактивной работы,
но скорость необходимо измерять на целевых компьютерах. Для приемки следует
фиксировать время до первого токена, tokens/s, время индексации 1 000 фрагментов,
OCR одной типовой страницы и пиковую RAM. GPU-ускорение первой версии разумно
делать через отдельный проверенный backend pack (например Vulkan), всегда
сохраняя гарантированный CPU fallback.

## Установка, первый запуск и обновления

1. Собрать backend в режиме one-folder. One-file упаковка не подходит: распаковка
   нескольких гигабайт при каждом запуске ухудшит первый старт и диагностику.
2. Сделать per-user offline installer без требования администратора. Для пилота
   достаточно Inno Setup; корпоративную MSI можно добавить после стабилизации.
3. Не писать изменяемые данные в `Program Files`. Использовать
   `%LOCALAPPDATA%\Atlas`; при обновлении никогда не удалять `data` и `models`.
4. Поставлять базовый GGUF и все рабочие OCR/RAG-модели заранее, чтобы первый
   запуск не требовал сети. Большую модель и coder-модель оформлять отдельными
   подписанными пакетами с SHA-256.
5. Супервизор должен предотвращать двойной запуск, выбирать свободный локальный
   порт, запускать `llama-server`, ждать `/health`, запускать Streamlit, открывать
   браузер и завершать дочерние процессы через Windows Job Object.
6. Обновлять приложение и модели независимо. Новую версию приложения ставить
   рядом, переключать после health-check и сохранять возможность отката. Модель
   не заменять автоматически без явного согласия и свободного места.
7. Логи ограничить техническими событиями. Не писать промпты, текст документов,
   ключи обезличивания и содержимое SQLite.

## Поэтапный план

### Этап A — доказательство backend-шва

- Добавить режим `LLM_BACKEND=llama_cpp` с `/v1/chat/completions`.
- Запустить текущие unit-тесты и отдельные contract-тесты клиента.
- На Windows вручную проверить одну GGUF на CPU: чат, RAG, код и JSON-интерпретатор.
- Сравнить 4–6B Q4 с текущей 9B на фиксированном наборе задач.

Критерий выхода: прикладной код Atlas не знает, запущен Ollama или llama-server,
а ответы проходят минимальный качественный порог.

### Этап B — переносимый backend без установщика

- Зафиксировать Python и wheels с hashes; собрать one-folder.
- Включить ML/OCR/Whisper-кэши и headless LibreOffice.
- Добавить супервизор, локальные пути и безопасное завершение.
- Проверить чистые Windows 10/11: CPU-only, NVIDIA/AMD/Intel, кириллица в путях,
  отсутствие сети, перезагрузка и обновление поверх существующих данных.

Критерий выхода: распакованный комплект запускается одним ярлыком без Python,
Docker, Ollama и ручного терминала.

### Этап C — установщик и обновление

- Собрать подписанный offline installer и manifest компонентов.
- Добавить проверку диска/RAM/CPU, контроль checksums и понятный первый запуск.
- Реализовать независимые app/model updates и откат приложения.
- Выполнить миграционный тест на копии существующего `data`.

### Этап D — только после пилота

- Решить по обратной связи, нужен ли WebView2 shell.
- Рассмотреть ONNX для embeddings/reranker и более легкий OCR только после
  сравнительного теста качества и совместимости существующих индексов.
- Добавить опциональный GPU pack и coder GGUF.

## Что еще нужно доказать до установщика

- Лицензионную совместимость и notices всех перераспределяемых моделей и
  бинарников, особенно выбранного GGUF, LibreOffice и FFmpeg.
- Работу FAISS wheel и SQLite FTS5 в замороженном Windows backend.
- Отсутствие сетевых обращений после установки, включая Hugging Face telemetry и
  ленивую загрузку Whisper/EasyOCR.
- CPU baseline на машине без AVX2 либо явно документированный минимум CPU.
- Стабильность загрузок из Streamlit при работе через shell/browser.
- Качественный порог модели 4–6B; без этого нельзя обещать отсутствие заметного
  ухудшения относительно 9B.

## Реализованный минимальный прототип

В `desktop/atlas_launcher.py` добавлен stdlib-only супервизор будущего
one-folder комплекта. Он уже фиксирует главный архитектурный шов:

- приложение и пользовательские данные физически разделены;
- backend выбирает свободные порты и слушает только `127.0.0.1`;
- сначала запускается `llama-server` и проверяется `/health`, затем Streamlit;
- модели Hugging Face принудительно работают offline;
- при остановке супервизор завершает оба дочерних процесса;
- режим `--check` проверяет состав комплекта без запуска и записи данных.

После сравнительного прогона для Desktop выбрана единая Qwen3.5-4B Q4_K_M с
контекстом 8192. `desktop/components.json` закрепляет точный GGUF Unsloth и
официальные Windows x64 CPU/Vulkan архивы llama.cpp `b10456` вместе с размерами,
revision и SHA-256. `desktop/prepare_runtime.py` загружает их в изолированный
staging, проверяет целостность и безопасно распаковывает архивы.

Нативная Windows-проверка подтвердила `/health` и генерацию ответа точным GGUF
на CPU и Vulkan. Launcher сначала пробует Vulkan, затем автоматически возвращается
к обязательному CPU backend. API llama-server защищён случайным ключом на каждый
запуск. Финальный Docker target не содержит `desktop/` и `tests/`; они входят
только в отдельный CI test-target.

Следующий технический прототип собрал официальный Windows embeddable Python
3.11.9. Desktop использует отдельный direct-requirements файл и lock из 83
конкретных Windows wheels; все URL и SHA-256 зафиксированы. Builder загружает
wheelhouse с повторными попытками, проверяет каждый SHA-256, устанавливает его с
`--no-index --only-binary=:all:` и удаляет build-only pip из результата.

Фактический распакованный Python runtime без pip занимает 2 553 169 007 байт,
wheelhouse — 540 761 719 байт. На Windows подтверждены SQLite 3.45.1 с FTS5,
FAISS 1.11.0, PyTorch/torchvision CPU, Sentence Transformers, EasyOCR,
faster-whisper, OpenCV, CTranslate2, Streamlit, Office/PDF-парсеры и
cryptography. Полный запуск из staging успешно поднял Vulkan llama-server и
Streamlit с health `ok`.

Idle-замер полного supervisor с Vulkan показал 3 039 686 656 байт working set и
4 113 227 776 байт private bytes; почти весь объём принадлежит llama-server.
Поскольку Desktop однопользовательский, `--parallel 1` заменяет четыре
стандартных слота одним и сохраняет контекст 8192. В отдельном замере private
bytes llama-server снизились примерно с 4,05 до 3,82 ГБ; working set почти не
изменился. `--no-host` выигрыша не дал. Следовательно, 8 ГБ RAM остаются
ограниченным профилем и требуют последовательной выгрузки LLM перед тяжёлым
OCR/RAG, а не только GPU-offload.

Launcher теперь назначает дочерние процессы в Windows Job Object с
`KILL_ON_JOB_CLOSE`. Жёсткая проверка подтвердила: после принудительного
завершения родителя число оставшихся дочерних процессов равно нулю.

Это еще не установщик. Проверенные GGUF, llama.cpp и Python runtime находятся
только в исключённом из Git локальном staging. Прототип пока не включает
LibreOffice, FFmpeg и готовые ML/OCR/Whisper-кэши. Следующий критерий — добавить
их в воспроизводимый one-folder каталог, добавить защиту от двойного запуска и
измерить пиковую RAM на целевой машине при реальной RAG/OCR-нагрузке.
